1. Methodology

What is this report?
This is a product-level evaluation of WeatherWise.ai. It answers the question: “Does the WeatherWise system (with its tools, RAG knowledge base, and multi-agent pipeline) produce better answers than just asking a raw LLM directly?”

The evaluation uses LLM-as-Judge — a technique where a separate LLM (the “judge”) scores each response against reference answers and success criteria defined by domain experts. This follows industry-standard practices from RAGAS and LangSmith for evaluating RAG and agentic systems.

The evaluation is multi-layered: deterministic code checks catch obvious failures first, then the LLM judge scores responses on multiple quality dimensions, and finally each success criterion is evaluated as a binary PASS/FAIL.

Why is the judge a different model?
Research shows that LLMs exhibit self-enhancement bias — they tend to rate their own outputs more favorably than outputs from other models. By using GPT-4o (OpenAI) to judge responses from Claude (Anthropic) and Gemini (Google), we eliminate this confound and get more objective quality scores.

What Is Being Compared

WeatherWise.ai (System Under Test) has access to:
• Live Xweather API via MCP tools (current conditions, forecasts, alerts)
• ChromaDB RAG knowledge base (atmospheric science documents)
• numexpr calculator for unit conversions and arithmetic
• Multi-agent routing (forecast, research, analyst specialists)
• Guardrails for input filtering and safety

Baselines (Raw LLMs) have access to:
• Only parametric training knowledge (no live data, no tools)
• No RAG retrieval, no real-time weather API calls
• No multi-agent routing or specialized agents

Expected outcomes: WeatherWise should dominate on factual grounding (live data vs stale training data) and completeness (tools fetch all required info). Baselines may score comparably on formatting and scientific accuracy (from training data). The Tools column in the summary table shows this structural difference: WeatherWise makes 3–5+ tool calls per query, baselines make 0.

Evaluation Pipeline

1
Code Assertions
Deterministic · Fast · No LLM cost
Checks structural properties of the response: presence of numeric values with units (e.g. “18 mph”), expected location names, intermediate math steps, citations, and multi-location mentions for comparative queries.
2
LLM Judge — Dimensional Scoring
1–5 per dimension · Weighted average
The judge LLM scores each response on multiple quality dimensions (e.g. factual grounding, completeness, scientific accuracy). Each dimension has a weight; the overall score is the weighted average. Pass threshold: overall ≥ 3.5 out of 5.0.
3
Binary Criteria
MUST / SHOULD per criterion
Each success criterion from the golden test case is evaluated as PASS or FAIL. Criteria prefixed MUST are hard requirements; SHOULD are soft. Overall pass requires all MUST criteria to pass AND ≥ 75% of SHOULD criteria to pass.
